## 2. 组织审批与提供方前提

- 读取：复用用户本人已有文档权限，不扩大访问范围。
- 成员检索：通过 HTTP 通讯录接口按姓名、工号或学号检索，并确认身份命名空间、同名区分字段；当前已验证。
- 视图写入：通过 HTTP `commitchanges` 实现新建、改名、筛选、分组、排序；当前已验证共享表格/看板视图，个人视图写入范围未验证。
- 字段属性写入：通过 HTTP `3017` 重命名、修改 USER 多选/通知、数字/日期格式、选项新增/改名/颜色，已验证。
- 查找引用与单向关联：通过 HTTP `3014`/`3017` 创建，关联单元格通过 `3013` 写入；多选与清空已验证。双向关联和固定值查找条件未验证。
- 公式写入：结构化 AST 编码为网页公式 token，已验证 `IF`/`ISBLANK`/`TODAY`、比较和算术。
- 视图列设置/删除：`3018`/`3024`/`3016`/`3033`/`3007` 已验证。
- 子表操作：`3001`/`3004`/`3002` 已验证；URL 单元格 `8:[{1:url,2:文本}]` 已验证。
- 动态“我”条件：编码为人员字段 `k35=true`，已写入并回读验证；实际筛选结果仍需至少两个已授权账号人工核对。

状态定义：`verified` 已有真实样本或契约测试；`local_only` 本地可用但提供方未验证；`unavailable` 缺少授权渠道或证据。

## 5. 结论与下一步

阶段 A 结论：**读取、成员、共享视图、字段属性、查找引用、单向关联、关联单元格和公式写入渠道均可用；双向关联、固定值查找条件等子集仍未验证**。因此：

1. 已完成阶段 B/E 的本地类型模型、成员身份校验、视图规范化、公式规则、配置计划与核对工具。
2. 成员检索与成员写入均通过 HTTP `commitchanges` 验证；共享表格/看板视图的创建、改名、筛选、分组、排序及动态“我”已验证；字段属性、查找引用、单向关联、关联单元格和公式也已通过真实写入与回读验证。双向关联、固定值查找条件和公式展示格式仍按能力矩阵拒绝。
3. 进入字段属性/引用/关联/公式前必须先取得经过许可且可验证的写入渠道，并补充：字段属性补丁协议、标题列身份保护、查找引用/关联配置模型、公式计算状态读取、字段/视图并发版本语义。
4. 四表实施按“快照 → 成员账号 → 人员/年度视图 → 引用/关联 → 公式 → 看板 → 整体核对”执行；未支持项在 `wecom_plan_changes` 中保留为 blocked/invalid，不用固定账号或整对象覆盖替代。

验证命令：`npm run check`、`npm test`、`npm run check:public`。线上只读核对使用 `wecom_capabilities`（`probe: true`）、`wecom_table_structure`、`wecom_read_view`、`wecom_plan_changes` 和 `wecom_verify_changes`。
